# Eval CLI reference (`cmd/eval`, `cmd/eval-gen`)

Moved out of `CLAUDE.md`. Golden-set format and the individual sets: `eval/golden/README.md`.

- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl` — retrieval evaluation against a golden set (see `eval/golden/README.md`)
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --judge [--judge-model <name>]` — retrieval + LLM-as-judge (faithfulness, answer relevance, context precision, plus **coverage** on rows that carry `expected_points`). Judge parsing is **tolerant** since Wave 4 (W4-R1): a score emitted as a numeric string is accepted and clamped to 1–5, and a boolean list whose length differs from the contexts/points is truncated or padded with an entry in `judge_warnings` — a sample is dropped only when the JSON is unparseable. The aggregate carries `faithfulness_n` / `answer_relevance_n` / `context_precision_n` / `coverage_n` and the printer shows `(n=…)` next to each mean (`judged_count` keeps its old meaning: questions with a Judge block). Pre-Wave-4 judge numbers stay comparable for well-formed responses — the same responses score the same — but `n` may now be higher, because samples that used to be dropped are kept. Since Wave 6 (W6-R4/R17), a decoder failure (a brace-balanced-but-invalid object — a raw newline, an unescaped quote, or a trailing comma inside a string; not truncation, not fences) triggers exactly **one** bounded retry, localized to the question's language, with the decoder's own error appended to the prompt; every attempted retry — success or failure — is recorded in `judge_warnings` as `retry:<metric>` and increments `rag_judge_retry_total{judge}` (shared by `cmd/eval`, the in-app/scheduled runner and the runtime RAGAS sampler, since all three call `internal/eval.Judge`). The parser itself stays strict — this is a bounded retry, not a tolerance loosening. Measured on the 24-question global-synthesis set: **0 retries, 0 remaining failures** (baseline: 2 decoder failures in 384 judge calls across the Wave 4/5 runs); the one `judge_errors` entry on that run was a transport timeout, which correctly never enters the retry path. **Comparability caveat:** the same Wave-6 change also edited the JSON-hygiene line in all four judge system prompts (`internal/prompts/eval_judge.go`), so judge scores from Wave 6 onward are not strictly byte-comparable to pre-Wave-6 numbers — including the Wave 4/5 flat/map_reduce judged runs and the pairwise records that decided the `chat_longcontext_mode = map_reduce` default; only the retry/failure counts above are a like-for-like comparison.
- `cd go-backend && ./cmd/eval/eval --pairwise-a A.json --pairwise-b B.json [--pairwise-out out.json] [--judge-model <name>]` — offline, position-debiased **pairwise preference judge** over two existing `--judge` reports (W4-R4): every question pair is judged in both orders and counts only when both orders agree, otherwise it is a tie. Prints wins/ties/losses from A's perspective, win rate with a 95 % Wilson interval (ties excluded), tie rate, and per-route + per-question tables; skipped/error pairs are counted and visible. Exit 0 (it is a measurement, not a gate), 2 on usage error. Both reports' questions must carry `kb_id` (the judge model resolves per KB). Optional golden field `expected_points` (≤ 12 points, ≤ 300 runes each) drives the coverage judge — absent means the judge is skipped, not scored 0. The global-synthesis set is **24** questions since Wave 5 (G01–G12 byte-identical, G13–G24 added, 6 points each), which is what made the pooled rule adequately powered.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context --team-id <uuid>` — per-team eval: every question dispatches through the real `RunTeamChat` (team must be attached + enabled on the KB; requires `--production-context`; incompatible with `--trajectory`; errors are hard per-question, never a silent standard-path fallback)
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--enhance …] [--hyde] [--multi-query] [--crag on|off] [--enumeration on|off] [--orchestrator-dispatch=true|false]` — eval through the production chat pipeline (CRAG, enumeration, contextual prefix, sandwich order). `--orchestrator-dispatch` defaults **true** (each question routes through the production orchestrator predicate; report records per-question `agent` + per-orchestrator aggregates); set `=false` for byte-stable diffs against pre-2026-05 retrieval-only runs, except that recency-listing-shaped questions now exercise the recency lister and window scoping, which pre-2026-09 runs did not. Since Wave 6 (Task 10), every question also carries `latency_ms` and per-question `agent.llm_calls` (a `CallCounter` wrapping every model-provider HTTP request — chat completion, streamed or unary, embedding, and rerank — for that question's whole `Search` call, classifier included); the aggregate (overall, per-route, per-orchestrator) gains `mean_latency_ms` (always printed, 0 is a valid latency) and `mean_llm_calls` (a pointer, `omitempty`, nil when no question in the bucket carried an `Agent` trace at all) — these are the cost half of the `query_type × orchestrator → recall/MRR/cost` measurement `--policy` (below) exists to produce.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --trajectory --orchestrator off|agentic|plan_execute|plan_execute_dag|supervisor|all [--judge]` — trajectory eval: per (question, orchestrator) emits the full agent decision sequence to `eval-trajectory.jsonl` + `.aggregate.json`. `--judge` adds four LLM judges (decomposition coverage, decision correctness, rewrite utility, tool-call correctness).
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --depth-buckets [--depth-buckets-min-chunks 4]` — position-aware analysis: adds a `depth_buckets` section (per-quartile relevant vs non-relevant counts, bucketed by chunkIndex/totalChunks) to surface position bias toward the start of long files. NOT a true RULER needle test.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--keep-raw on|off] [--bm25-mode ts_rank|bm25] [--recency-boost on|off] [--refresh-bm25-stats]` — Wave-2 ablation overrides on top of production-parity mode: each flag overlays the named site_config for this run only (no `site_configs` mutation), empty/unset reads the live value. `--refresh-bm25-stats` recomputes BM25 stats (creating the stats tables idempotently if missing) for every KB the golden set references, across every dim table with rows for that KB, before running — use it ahead of a `--bm25-mode bm25` run against a KB that hasn't had a recent stats refresh.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--longcontext on|off] [--longcontext-mode flat|map_reduce] [--golden-query-type]` — Wave-3 run overrides: the two `--longcontext*` flags overlay `chat_longcontext_enabled` / `chat_longcontext_mode` for this run only (empty = live value, no `site_configs` mutation, one wrapper for both); `--golden-query-type` feeds each golden row's own `query_type` into retrieval instead of classifying the question (orchestrator dispatch still classifies independently — deliberately). Used for the flat vs `map_reduce` A/B against `eval/golden/global-synthesis-de.jsonl`. The live default is `map_reduce` since Wave 5, so an explicit `--longcontext-mode flat` is what a flat run needs now.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context [--conflict-surfacing on|off]` — Wave-5 overlay for `chat_conflict_surfacing_enabled` (empty = live value, no `site_configs` mutation, composes with the other chat-layer overlays). `on` makes every turn whose assembled set spans ≥ 2 distinct files run the conflict / supersession pass and records the resulting bare array per question as `conflicts` in the JSON report — the same value a chat turn persists and streams. Effective on the standard path and, under `--orchestrator-dispatch`, on the Supervisor path. The report gains a `Conflict surfacing:` block only when at least one question carries an entry, so a flag-off report stays byte-stable. `cmd/eval` wires a `FileDateLookup` of its own (`eval.WithFileDates`) — without one every date line reads "unknown" and the detector is instructed not to guess a direction, which would make the supersession measurement vacuous.
- `cd go-backend && ./cmd/eval/eval --golden ../eval/golden/<set>.jsonl --production-context --orchestrator-dispatch=true --policy '<json>'` — Wave-6 (W6-R6/R7) per-run overlay for `chat_orchestrator_policy`, validated by the same `chatpolicy.ValidateOrchestratorPolicyJSON` the save path uses BEFORE the run (an invalid document is a usage error, exit 2, never a silently ignored flag); each question's report gains `agent.policy_rule` and the human summary an `Orchestrator policy:` block whenever at least one question carried a rule. `--chat-overlay key=value` (repeatable, W6-R18) is the generic escape hatch for any OTHER chat-layer `site_config` key the same reader serves (e.g. `chat_conflict_max_chunks`); `--chat-overlay chat_orchestrator_policy=…` is rejected — use `--policy`, which validates. Both compose with the other chat-layer overlays (`--longcontext*`, `--conflict-surfacing`) through the one shared overlay wrapper; empty = live site_config.
- `cd go-backend && ./cmd/eval/eval [--pairwise-out pooled.json] --pairwise-pool a.json b.json` — pools two pairwise results over their **decisive** pairs (ties excluded from every denominator, as in `--pairwise-a/-b`), recomputing rather than averaging the two win rates, and prints Wilson bounds from **both** perspectives (they reflect, they do not swap). **Flag ordering is load-bearing:** Go's `flag` package stops parsing at the first positional argument, so `--pairwise-out` must come BEFORE the two paths; a trailing flag is rejected with an explanation rather than silently writing nothing. The inputs must put the same configuration on side A — the command warns but cannot check, since a pairwise JSON carries no report paths. A file without a `pairs` key is refused, so handing it an eval report cannot silently read as "0 decisive pairs". Exit 0 on a completed pooling, 2 on a usage error.
- `cd go-backend && ./cmd/eval/eval --print-keyword-sql "<query>" --kb-id <uuid> [--top-k 50]` — diagnostic: prints the keyword arm's SQL for that query in **both** scoring modes (`ts_rank` and `bm25`), with the KB's real resolved settings (chunk table, text-search config, simple arm, k1/b, dim-keyed stats tables), as one JSON document on stdout, then exits 0. Runs no search and needs no golden set; each mode carries a placeholder-free `executable_sql` for `EXPLAIN (ANALYZE, BUFFERS)`. Used by `eval/fixtures/bm25-scale/time-keyword-sql.sh`.
- Multi-turn replay: a golden set whose rows carry a `turns: [...]` array (e.g. `eval/golden/multi-turn-de.jsonl`, gitignored — JLU-internal) is expanded per-turn and requires `--production-context` (turns bypass orchestrator dispatch and teams entirely — always the standard `PrepareChatContext` path; `--team-id` is rejected on a golden set with turns). `--question-id MT01` runs a whole conversation; `--question-id MT01#t2` runs one expanded turn (its preceding turns still build its `History`). Report gains `turn_kind_aggregates` (recall/MRR/nDCG per `corpus`/`pronoun_ref`/`topic_shift`/`answer_ref`/`post_abstain`). Multi-turn sets are `cmd/eval`-only: `internal/eval.ParseGoldenSetContent` (the DB/admin eval path) rejects any row carrying `turns` outright, since only `cmd/eval` calls `ExpandTurns` to replay one — a saved golden set with turns must be run from the file, never from the admin UI/DB copy. That rejection is unchanged, but since Wave 6 (W6-R3) `ParseGoldenSetContent` itself accepts **either** a JSON array (the original DB shape) **or** JSONL with `#`-comment/blank lines (the shape a file upload carries) — the first non-whitespace byte decides which (`[` → array, else JSONL), sharing `ParseGoldenSetJSONL`'s line parser — so a set authored as JSONL can be saved through the admin UI directly, not only run from the file via `cmd/eval`. See `eval/golden/README.md` §"Multi-turn set".
- `cd go-backend && go build ./cmd/eval-gen`
- `cd go-backend && ./cmd/eval-gen --kb-id <uuid> [--lookup 20] [--complex 10] [--enumeration 5] [--multihop 5] [--lang de|en] [--out <path>] [--model <m>]` — synthesize a **draft** golden set from a KB's ingested chunks (lookup / complex / enumeration / multi-hop via semantic-neighbor pairing; emits both `must_cite_file_ids` and `must_cite_file_names`). Output is a curation draft — review before use. Also available async from the admin Eval tab ("Generate from corpus"), which saves the result into `eval_golden_sets` (migration 0049 `eval_golden_set_jobs` tracks job status; description prefix `auto-generated from corpus`).
- `eval/fixtures/seed-spreadsheets.sh` / `eval/fixtures/seed-cert.sh` — fixture seed scripts for the structured-spreadsheet and CERT-recency golden sets respectively; both idempotent (skip already-ingested titles), both require a reachable dev stack + admin credentials. `seed-cert.sh` additionally backdates `files.created_at` per `eval/fixtures/cert-advisories/manifest.tsv` and writes `eval/golden/cert-recency-de.local.jsonl`; `--restamp --kb-id <uuid>` re-runs just the backdating against an already-seeded KB. See `eval/golden/README.md` §"CERT recency set".
